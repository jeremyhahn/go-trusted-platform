# Client-Side Network Setup for Device Profile Activation

> **Status: ARCHIVE — historical record. Do NOT build from this document.**
> Last verified: 2026-10-13 · Replaced by [api.md](api.md) and [user.md](user.md). The self-service profile carries `admittedNetwork` and `provisioningNetwork`, not `production_network`.

## Overview

The `trusted-platform-network` service provides automated, client-side network configuration during system boot. It fetches the device profile from the platform API using mTLS (IDevID certificate), applies network configuration, and triggers device activation on the platform.

This service is essential for devices undergoing Trusted Platform enrollment, as it enables automatic network configuration transition from provisioning to production networks.

## Components

### Network Setup Script
**File:** `/usr/local/bin/trusted-platform-network.sh`

A production-grade bash script that handles:
- Prerequisites validation (certificates, required commands)
- Exclusive locking to prevent concurrent execution
- Device profile fetching via mTLS API
- Profile structure validation
- Network configuration parsing and application
- systemd-networkd configuration generation
- Network connectivity verification
- Device activation on platform API
- State persistence

### Systemd Service Unit
**File:** `/lib/systemd/system/trusted-platform-network.service`

Orchestrates the network setup process with:
- Early boot execution (after network.target and platformd.service)
- Proper dependency management
- Security hardening with systemd features
- CAP_NET_ADMIN capability for network interface configuration
- Resource limits and process isolation
- Journal-based logging

## Architecture

```
Boot Process
    ↓
systemd starts trusted-platform-network.service
    ↓
/usr/local/bin/trusted-platform-network.sh executes
    ↓
Acquire exclusive lock
    ↓
Fetch device profile (via mTLS)
    ↓
Validate profile structure
    ↓
Extract production network config
    ↓
Generate systemd-networkd config files
    ↓
Reload systemd-networkd
    ↓
Verify network connectivity
    ↓
Call device activation endpoint
    ↓
Save state file
    ↓
Service completes
    ↓
Systemd continues boot to multi-user.target
```

## Configuration

### Environment Variables

The service respects the following environment variables (can be set in `/etc/trusted-platform/network.env`):

| Variable | Default | Description |
|----------|---------|-------------|
| `PLATFORMD_ENDPOINT` | `https://localhost:8443` | Platform daemon API server URL |
| `PLATFORM_IDEVID_CERT` | `/etc/trusted-platform/certs/idevid.crt` | IDevID certificate path |
| `PLATFORM_IDEVID_KEY` | `/etc/trusted-platform/certs/idevid.key` | IDevID private key path |
| `PLATFORM_CA_CERT` | `/etc/trusted-platform/certs/ca.crt` | CA certificate for server verification |
| `DEBUG` | `0` | Enable debug logging (set to `1` for verbose output) |

### Configuration Directories

| Path | Purpose |
|------|---------|
| `/etc/systemd/network/` | Generated networkd configuration files |
| `/etc/trusted-platform/` | Platform certificates and configuration |
| `/var/lib/trusted-platform/` | Runtime state and logs |
| `/var/log/trusted-platform/` | Script output logs |
| `/var/backups/trusted-platform/network/` | Backup of previous network configs |

## Device Profile Structure

The network setup script expects the device profile JSON response from `GET /api/v1/device/profile` to contain:

```json
{
  "id": 1,
  "name": "device-001",
  "role": "server",
  "production_network": {
    "vlan": 100,
    "static_ip": "192.168.1.100/24",
    "gateway": "192.168.1.1",
    "dns": ["8.8.8.8", "1.1.1.1"],
    "auth_method": "none"
  },
  "provisioning_network": { ... },
  "quarantine_network": { ... }
}
```

The service specifically uses the `production_network` configuration to:
1. Identify the VLAN to transition to
2. Assign static IP address (if specified)
3. Configure default gateway
4. Set DNS resolvers

## systemd-networkd Configuration

The script generates configuration files in `/etc/systemd/network/` using the standard systemd-networkd format:

**Example generated config:** `/etc/systemd/network/10-eth0.network`

```ini
# Generated by trusted-platform-network.sh
# DO NOT EDIT MANUALLY

[Match]
Name=eth0
VLAN=100

[Network]
DHCP=no
DNS=8.8.8.8 1.1.1.1
Address=192.168.1.100/24
Gateway=192.168.1.1
```

## Security Considerations

### mTLS Authentication
- All API calls use client-side TLS authentication with IDevID certificate
- CA certificate ensures server verification
- Protects against unauthorized access to device profile and activation endpoints

### Process Isolation
- Runs with `CAP_NET_ADMIN` capability (minimal required privilege)
- Restricted to network-related system calls
- Cannot access user home directories or sensitive system paths
- Protected kernel tunables and control group settings

### File Permissions
- Service files owned by root with restricted permissions (0644)
- Script executable only by root (0755)
- State files protected with 0600 permissions
- Backup files preserved with timestamps

### Credential Handling
- No credentials stored in service file or script
- Certificate paths externally configurable
- No logging of sensitive data (credentials, private keys)
- Secure temporary file handling with trap cleanup

### Locking Mechanism
- Exclusive lock prevents concurrent execution
- Prevents race conditions during network reconfiguration
- PID file for process tracking

## API Integration

### Device Profile Endpoint
**Request:**
```bash
GET /api/v1/device/profile
Authorization: mTLS (IDevID certificate)
Accept: application/json
```

**Response:**
```json
HTTP 200 OK
Content-Type: application/json

{
  "id": ...,
  "name": ...,
  "production_network": { ... }
}
```

### Device Activation Endpoint
**Request:**
```bash
POST /api/v1/device/activate
Authorization: mTLS (IDevID certificate)
Content-Type: application/json
```

**Response:**
```
HTTP 200 OK | 201 Created | 204 No Content
```

## Troubleshooting

### Service Status
Check service status and logs:
```bash
systemctl status trusted-platform-network.service
journalctl -u trusted-platform-network.service -n 50
```

### Manual Execution
Run the script manually with debug output:
```bash
DEBUG=1 /usr/local/bin/trusted-platform-network.sh
```

### Common Issues

#### "Certificate not found"
**Symptom:** Error in logs about missing `/etc/trusted-platform/certs/idevid.crt`

**Solution:** Ensure certificates are properly installed during platform enrollment:
```bash
ls -la /etc/trusted-platform/certs/
```

#### "API request failed with HTTP 503"
**Symptom:** Service fails to fetch profile from platform API

**Solution:** Verify platformd.service is running and network connectivity exists:
```bash
systemctl status platformd.service
systemctl status systemd-networkd.service
```

#### "Failed to restart systemd-networkd"
**Symptom:** Network configuration generated but not applied

**Solution:** Check systemd-networkd logs and configuration syntax:
```bash
journalctl -u systemd-networkd.service
systemd-networkd-wait-online.service --status
```

#### "Device activation failed"
**Symptom:** Network configured but device not activated on platform

**Solution:** Verify API connectivity and check platform logs:
```bash
curl -v --cert /etc/trusted-platform/certs/idevid.crt \
       --key /etc/trusted-platform/certs/idevid.key \
       --cacert /etc/trusted-platform/certs/ca.crt \
       https://localhost:8443/api/v1/device/activate
```

### State File
The service creates `/var/lib/trusted-platform/network-state.json` on successful completion:
```json
{
  "timestamp": "2025-12-21T12:34:56Z",
  "profile_id": "1",
  "device_name": "trusted-device-001"
}
```

If this file exists and is recent, the service has already completed successfully.

## Restart and Recovery

To manually restart network configuration:
```bash
systemctl restart trusted-platform-network.service
```

To restore previous network configuration from backup:
```bash
# List available backups
ls -la /var/backups/trusted-platform/network/

# Restore a specific backup
cp /var/backups/trusted-platform/network/10-eth0.network.1703076896 \
   /etc/systemd/network/10-eth0.network

systemctl daemon-reload
systemctl restart systemd-networkd
```

## Performance Characteristics

| Operation | Typical Duration |
|-----------|------------------|
| Lock acquisition | < 100ms |
| Certificate validation | < 50ms |
| API profile fetch | 100-500ms |
| Profile validation | < 50ms |
| Config generation | 100-200ms |
| systemd-networkd reload | 500-1000ms |
| Connectivity verification | 2-10s (with retries) |
| Device activation | 100-500ms |
| **Total end-to-end** | **2-15 seconds** |

The service uses a one-shot execution model and does not consume resources during normal system operation after boot.

## Integration with ISO Customization

The network setup files are automatically included in the ISO during customization:

1. **Script** copied to overlay: `/usr/local/bin/trusted-platform-network.sh` (0755)
2. **Service** copied to overlay: `/lib/systemd/system/trusted-platform-network.service` (0644)

The customization process (via `pkg/iso/customize.go`) ensures these files are present in the installed system.

## Extension Points

The script is designed for extensibility:

### Custom Hook Scripts
Add additional setup logic by creating hook scripts:
- `/etc/trusted-platform/network-setup.d/pre-*.sh` - Before profile fetch
- `/etc/trusted-platform/network-setup.d/post-*.sh` - After activation

### Custom Network Config
Override network configuration by modifying `/etc/systemd/network/` files after service completion.

### Additional Phases
The device profile supports `provisioning_network` and `quarantine_network` in addition to `production_network`. Future enhancements can support configuration of these phases.
