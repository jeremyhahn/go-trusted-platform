## The problem

Every layer of this platform needs keys — CA signing keys, per-tenant DEKs,
per-image DEKs, node identities, sealed secrets — and the deployments it targets
differ completely in where those keys are allowed to live: a TPM, a PKCS#11 HSM,
a cloud KMS, or software in a lab.

## The shape chosen

**Re-export the stack's key management; implement none of it.** go-xkms owns
hardware and cloud crypto; go-quicbaas composes it; this repository exposes it as
the platform product's KMS surface (docs/00 L5).

The evidence is the package tree: **there is no `pkg/kms` in this repository**
(verified 2026-08-18). What exists is service and transport code under
`pkg/api/daemon/kms_*`, `pkg/api/grpc/kms_service.go`,
`pkg/webservice/v1/rest/kms/` and `pkg/cli/commands/kms/`.

### Alternatives rejected

| Alternative | Why it was rejected |
|---|---|
| **Implement key management in the platform** | Two key-management implementations means two sets of crypto bugs, two FIPS boundaries and two audit surfaces. The stack owns it (docs/00 L2), and the absence of `pkg/kms` is the enforcement. |
| **A single fixed backend** | Key custody is a deployment decision. Hardware TPM, PKCS#11, cloud KMS and software backends all have to be reachable through one surface, which is what `BackendStatus` reports. |
| **Handling key bytes in this layer** | This repository sits above Layer 3, so it uses the stack's owned key abstractions rather than coding protected memory itself. Key bytes never enter this layer. `ExportKey`'s CLI counterpart being unimplemented is the conservative side to be wrong on. |
| **Re-encrypting data on key rotation** | Rotation would become an outage proportional to data volume, so it would not happen. `Rewrap` re-encrypts to the latest key version and leaves plaintext alone. |
| **Treating AEAD invocation limits as advisory** | AES-GCM nonce reuse is a break, not a degradation. Limits are tracked per key with a dedicated CLI subtree, and exceeding one surfaces as `StatusResourceExhausted` rather than being silently ignored. |
| **Shipping the CLI's secrets subtree half-working** | Every `kms secrets` verb calls the go-quicbaas SDK secrets client (`Security().Secrets()`), the same client the REST surface uses, and stores the value the way REST does, so either surface reads what the other wrote. The one verb the SDK has no call for, `watch`, refuses with the typed `ErrSecretsSDKGap` naming `SecretsClient.Watch`; it does not poll or reach go-xkms. A half-working secrets store would be worse than an absent one, because callers would trust it. |

## Trust boundaries

1. **Caller → KMS.** Crossed by a scoped platform token on gRPC. **Not crossed
   by any scope check on MCP** — no KMS tool is in the MCP authorization map, so
   an MCP client with a valid token can decrypt and sign with any key
   ([api.md](api.md) §6).
2. **Platform → backend.** Key material stays on the backend side. The platform
   layer holds handles and ciphertext, not keys.
3. **DEK envelope.** Per-tenant and per-image DEKs are generated by the KMS and
   wrapped by a KMS key. A caller that generates its own DEK has left the model.
4. **AEAD invocation budget.** A key that exceeds its safe invocation count is a
   broken key, and the only current way to see that coming is a CLI report.

## Data flow — encrypting a tenant's data

1. Tenancy asks the KMS for a **DEK** (`GenerateDataKey`).
2. The DEK is returned wrapped by a KMS key; the wrapped form is what is stored.
3. Data is encrypted under the DEK.
4. Rotation calls **`Rewrap`**: the DEK is re-encrypted to the latest key
   version. Layer bytes and tenant data are untouched.

That is why rotation is a routine operation rather than a migration.

## What this feature deliberately does not do

- **It does not implement key management, crypto primitives, or backends.**
- **It does not hold key material.**
- **It does not re-encrypt data on rotation.**
- **It does not expose AEAD safety limits over any API** — currently a gap
  ([api.md](api.md) §5), not a decision.
- **It does not watch secrets.** `kms secrets watch` refuses until the SDK
  secrets client has a `Watch` call ([cli.md](cli.md) §7).

## Overview

The Trusted Platform KMS provides distributed key management through direct QuicBaaS integration. The architecture leverages QuicBaaS's native KMS service with go-xkms backends for hardware security support including TPM 2.0 and PKCS#11 HSMs.

**Implementation Status:**
- gRPC API: 100% complete
- REST API: 100% complete (99.9% test coverage)
- CLI Commands: 100% complete
- Integration Tests: Framework complete, adapters implemented

## Backend Selection

go-xkms supports multiple backends with automatic routing:

```
+-----------------------------------------------------------------------+
|                        Backend Selection                               |
+-----------------------------------------------------------------------+
|                                                                        |
|   1. Check explicit location in key attributes                         |
|      - KeyLocationSoftware -> Software backend                         |
|      - KeyLocationTPM -> TPM 2.0 backend (if available)                |
|      - KeyLocationHSM -> PKCS#11 backend (if configured)               |
|                                                                        |
|   2. Check algorithm compatibility                                     |
|      - Ed25519, Ed448 -> Software only (TPM doesn't support)           |
|      - AES-GCM, ECDSA, RSA -> TPM or Software                          |
|                                                                        |
|   3. Use default location from configuration                           |
|                                                                        |
|   4. Fallback logic                                                    |
|      - If TPM requested but unavailable -> Fall back to software       |
|      - Log warning for fallback                                        |
|                                                                        |
+-----------------------------------------------------------------------+
```

## Security Model

### Key Protection

| Layer | Protection Method |
|-------|-------------------|
| At Rest (Software) | Encrypted with DEK in QuicBaaS |
| At Rest (TPM) | Sealed to TPM hierarchy, PCR-bound |
| In Transit | TLS 1.3, mTLS for internal communication |
| In Memory | Secure zeroing after use, optional caching |

## CA Integration


## Recovery and Backup

### Software Keys

- Backed up via QuicBaaS snapshots
- Can be exported with key wrapping
- Replicated across cluster nodes

### TPM Keys

- Platform-bound, cannot be backed up directly
- Use key escrow with authorized recovery
- Multi-platform deployments use separate keys

### HSM Keys

- HSM-specific backup procedures
- Key cloning to backup HSM
- Recovery procedures per HSM vendor
