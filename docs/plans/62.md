# Plan: #62 Secure Boot keys in protected memory

## Objective

Secure Boot private key material never sits in ordinary heap strings or
leftover files: generation, signing and staging hold it in memguard enclaves
or wipe their buffers, and the files that must exist are written owner-only.

## Slices (in order)

1. r62a (PR #2363, landed on the row branch): `provisionSecureBootEntry` keeps
   each generated private key in a memguard enclave (`enclaveSecureBootKey`)
   and writes it through `storeNTSKey`, certificate first.
   Tests: pkg/app/secureboot_provision_test.go (enclave destroyed, write order).
2. Key loaders wipe their buffers; the module-signing bundle is replaced
   owner-only (pkg/secureboot/modulekey.go, pkg/authenticode/filesigner.go,
   pkg/iso customize/build).
   Tests: modulekey_test.go, filesigner_test.go, build_additional_test.go,
   customize_config_test.go.
3. Main merges plus the overlay capabilities fixture fix
   (router_overlay_configured_test.go passes the root-routes argument).
4. r62b: `ProcessSecrets` resolves `kms://` into an enclave instead of a
   string. Tests: enclave-returning resolver, no string copy left.
5. r62c: wipe the Secure Boot key file copies in pkg/iso / firstboot after
   writing. Tests: staged copy is gone after the stage step.
6. r62d: keys generated behind a KMS key handle (waits on go-quicbaas#136).

## Out of scope

- KMS-side key generation before go-quicbaas#136 is tagged.
- Hardware Secure Boot tier (integration-test-secureboot-hw).
- Any change to the wire contract or the overlay capabilities endpoint.
