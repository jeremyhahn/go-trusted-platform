# Plan: #1691 SPEC row `policy-engines` — OPA behind one build tag

## Objective

`docs/SPEC.md` asks for "OPA behind one build tag". Today
`pkg/policy/opa/engine.go` and `pkg/compute/container/opa_engine.go`
import OPA unconditionally. Put both behind the `opa` tag, keep the
exported API in a `!opa` stub that returns `ErrOPANotBuilt`, and add `opa`
to the Makefile `BUILD_TAGS` so default builds keep OPA.

## Slices (one PR)

1. Tests (`!opa`):
   - `pkg/policy/opa/engine_noopa_test.go`:
     `TestEngine_NoOPABuild_ReturnsErrOPANotBuilt` — every engine
     method returns `ErrOPANotBuilt` (`errors.As`).
   - `pkg/compute/container/opa_engine_noopa_test.go`:
     `TestOPAEngine_NoOPABuild_ReturnsErrOPANotBuilt` —
     `NewOPAEngine` returns `ErrOPANotBuilt` (`errors.Is`).
2. Change:
   - `//go:build opa` on both engines and their OPA-only tests.
   - `engine_noopa.go` / `opa_engine_noopa.go` (`!opa`) with the
     same exported API.
   - `ErrOPANotBuilt` in each package's untagged `errors.go`, so callers
     can test for it under both tag sets.
   - `Makefile`: `opa` in `BUILD_TAGS`.
3. Docs: `docs/security/engineering.md` records the tag.

`pkg/sdn/gateway/proxysvc/opa.go` uses `opa.NewOPAEngine` and keeps
compiling under both tag sets through the stub. Its OPA evaluator tests
(`opa_test.go`) need the real engine, so that file carries `//go:build opa`.

## Out of scope

- Any go.mod change; dropping the OPA module from go.mod.
- Other policy engines in the SPEC row.
