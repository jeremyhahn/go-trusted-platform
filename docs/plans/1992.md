# Plan #1992: invitation roles come from IAM (SPEC row 113)

## Objective

The invitation REST handler validated `req.Role` against a hard-coded map
(`ValidRoles` / `IsValidRole` in `pkg/webservice/v1/invitation/types.go`).
The set of assignable roles must come from IAM instead.

## Slices

1. Tests (`test(invitation)` commit):
   - a fake `RoleLister` in `handler_test.go`, passed to every `NewHandler`;
   - `NewHandler` refuses a nil `RoleLister`;
   - Create: a listed role is accepted (201), an unlisted role gets 400,
     a `ListRoles` error gets 500 and the invitation service is not called;
   - `TestIsValidRole` removed.
2. Fix (`fix(invitation)` commit):
   - `RoleLister` interface in `handler.go` with the IAM SDK client's
     `ListRoles(ctx, *platformv1.ListIAMRolesRequest) ([]*platformv1.IAMRole, int64, error)`;
   - `HandlerParams.RoleLister`, refused when nil (`ErrMissingRoleLister`);
   - Create lists the tenant's roles and accepts `req.Role` only if an
     `IAMRole.Name` equals it;
   - `ValidRoles` and `IsValidRole` deleted.

## Wiring

No code in `pkg` or `cmd` builds `invitation.HandlerParams` (the router uses
`pkg/webservice/v1/rest/invitation`), so there is no caller to wire with the
platform IAM client in this row. The lane report says so.

## Out of scope

- go.mod, go.sum, .github/workflows.
- The `rest/invitation` package and any other row.
- Paging through more than the first page of `ListRoles`.
