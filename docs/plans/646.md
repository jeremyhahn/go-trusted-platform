# #646 main-fix: integration legs on PR #2030

Two independent causes keep the integration legs red; each has its own slices.

## Part A: the supervised datapath child activates the load-balancer

### Objective

Under the gatewayd supervisor the datapath child fails its start at the
`fhrp-sweep` step: it reads `<data>/fhrp/vips.json` and gets EACCES, so the
load-balancer it hosts is never reported active and the supervised gateway's
startup fails (test/integration/proxy TestGatewaydSupervisor*).

Cause: the datapath class stays uid 0 but keeps only CAP_NET_ADMIN and
CAP_NET_RAW (no CAP_DAC_OVERRIDE / CAP_DAC_READ_SEARCH). Supervisor
`ensureStateDir` grants search on the data directory and owns the state
directory only for Unprivileged classes, so a root child cannot traverse a
0700 data directory another user owns.

### Slices

1. Test: `TestEnsureStateDir_TheRootDatapathChildCanTraverseTheDataDirectory`
   (pkg/sdn/gateway/process/process_test.go): a non-Unprivileged definition
   with a StateDir gets the data directory searchable for 0:0 and the state
   directory chowned to 0:0.
2. Fix: `ensureStateDir` grants traverse and state-dir ownership for every
   definition with a StateDir, with the credentials the child runs with
   (service account when Unprivileged, the supervisor's own uid/gid
   otherwise). State-file hand-over stays Unprivileged-only.

### Out of scope

- Adding DAC capabilities to the datapath class.
- The integration harness's data-directory layout.

## Part B: REST KMS calls 404 on the daemon REST listener

### Objective

The integration legs (PR #2030 base) fail every keyed KMS call over REST with
`REST API error (status 404): 404 page not found`. The harness REST adapter
(test/integration/kms/rest_adapter.go) and the SDK REST transport
(sdk/go/transport/rest) speak the KMS contract of docs/kms/api.md, which the
webservice KMS router (pkg/webservice/v1/rest/kms) serves:
`POST /api/v1/kms/{encrypt,decrypt,sign,verify}/{name}`, `/deks`, `/secrets`.

`platformd serve --rest-port` (build/docker/devcontainer/run-integration-tests.sh)
serves REST from the daemon's own router (pkg/api/daemon/rest_service.go). Its
KMS routes come from pkg/api/rest/kms_handlers.go, an older contract: crypto on
bare paths with `key_id` in the body (`POST /api/v1/kms/sign`), no DEK or
secrets routes. Those requests match no route, and mux answers its plain 404.

### Slices

1. Test: `TestDaemonREST_KMSRoutesReachTheirHandlers` (pkg/api/daemon) sends
   the adapter's method+paths through the daemon route table and fails on any
   "404 page not found". Fails on sign/verify/encrypt/{id}, deks, secrets.
2. Fix: `RESTServer.SetKMSRouter` mounts the webservice KMS router
   (the docs/kms/api.md contract) under /api/v1 on the daemon REST router,
   ahead of the legacy handlers, from the platform KMS backend's SDK KMS and
   Crypto clients plus the App SDK's DEK and Secrets clients; daemon.go wires
   it where it wires SetKMSHandlers. Legacy-only paths (bare crypto, export,
   batch, rewrap, status) still reach the legacy handlers.

### Out of scope

- Removing the legacy pkg/api/rest KMS handlers (other callers, own row).
- Running the integration legs (Docker; CI runs them).
