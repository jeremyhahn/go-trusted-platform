# Plan #1995: MCP tool permissions decided by the IAM PEP (SPEC row 116)

## Objective

`AuthorizationChecker.AuthorizeTool` (pkg/api/mcp/authz.go) decides an
unscoped tool call (legacy `ValidateToken` path, or authService only) by
splitting the permission with `strings.SplitN` and asking
`authService.CheckPermission`. The IAM PEP must decide it instead.

## Findings (slice 1)

- In the daemon, `mcpConfig.AuthorizationService` is either the shared
  `platformTokenValidator` (claims path: always `authScoped`, never reaches
  the fallback) or the `QuicBaaSAuthAdapter` from `createMCPAuthAdapter`,
  whose `CheckPermission` already asks its `iam.PEPClient`.
- The checker is built in `pkg/api/mcp/server.go` (`NewServer`,
  `SetAuthorizationService`), so the daemon wiring needs a
  `ServerConfig.PEPClient` field and a `WithPEPClient` option.
- `dragondb_auth_test.go` already has `mockPEPClient` (checkResp, checkErr).
- Many tests (authz_completeness_test, authz_test, platform_token_test,
  phase35/luks/daemon_provision authz tests) drive the fallback through an
  `AuthorizationService` fake; "nil PEP -> denied" breaks them, so they move
  to a PEP fake in the fix commit.

## Slices

1. test: `authz_test.go` cases for the unscoped path with a legacy
   `mockAuthManager` (claims sub/tenant_id/roles): PEP allow -> nil,
   PEP deny -> AuthErrorPermissionDenied, PEP error -> denied,
   nil PEP -> denied; assert the CheckRequest subject, resource and action.
2. fix: `pep iam.PEPClient` field + `WithPEPClient`; the fallback reads the
   caller from `authManager.GetTokenClaims` (no authManager -> denied),
   cuts the permission at the first `:` (`strings.Cut`), and calls
   `pep.Check`; `ServerConfig.PEPClient` passed in `NewServer` and kept in
   `SetAuthorizationService`; daemon sets `mcpConfig.PEPClient =
   d.iamService.PEP()` when IAM is up. Move the broken fake-authService
   tests to the PEP fake.
