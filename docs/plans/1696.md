# #1696: wire the FHRP speaker into gatewayd

## Objective

`pkg/sdn/fhrp` has a complete VRRPv3 speaker, but gatewayd never builds
it: `serviceBuilders` has no `fhrp` entry and `GatewayConfig` has no
`fhrp` section (docs/gateway/engineering.md, "not in gatewayd yet").
This row makes an enabled `fhrp:` section start the speaker as a gateway
service in the datapath process.

## Slice 1 (this lane)

Tests first (`test(gateway): ...`):

- `TestBuildFHRP_StartsSpeakerWithInjectedTransport`: an owner group
  (priority 255) over a fake Transport and Programmer; Start opens the
  group's socket on the configured interface and claims its address.
- `TestBuildFHRP_InvalidConfigRefused`: a group with VRID 0 is refused by
  `GatewayConfig.Validate` with `*ErrFHRPConfigInvalid` and by
  `buildFHRP` with `*ErrServiceStartFailed`.
- `TestEnabledServices_FHRP`: `fhrp` is enabled only when the section is.
- `TestClassTable_FHRPRunsInTheDatapath` (process): `fhrp` maps to the
  `datapath` process.

Change (`feat(gateway): ...`):

- `ServiceFHRP = "fhrp"` (node.go); `GatewayConfig.FHRP *fhrp.Config`
  (types.go), in `EnabledServices` when `Enabled`, validated in
  `GatewayConfig.Validate` (typed `ErrFHRPConfigInvalid`, errors.go).
- `HostRuntime.FHRPTransport` / `FHRPProgrammer` (runtime.go); nil falls
  back to `fhrp.NewRawTransport` / `fhrp.NewNetlinkProgrammer`.
- `buildFHRP` and the `fhrpBackend` adapter (handlers.go).
- `ServiceFHRP` among the `datapath` services (process/class.go).

Docs: docs/gateway/engineering.md drops the "not in gatewayd yet" line.

## Codex #1716 failed startup rollback

- A runner whose rollback at a failed Start could not release its VIP
  stays pending (`Speaker.ReleasePending`), and backedServiceHandler
  keeps such a service for its next Start or Stop
  (`TestSpeaker_FailedRollbackKeepsTheVIPPendingThroughRestartAndStop`,
  `TestBackedFHRPHandler_FailedRollbackIsCleanedUpOnRestartAndStop`).

## Codex #1716 round 6

- No `hostfw.vrrp` setting: VRRP is admitted only on enabled FHRP groups'
  interfaces, which `buildHostFW` passes as `hostfw.Deps.VRRP`
  (`TestConfig_HasNoVRRPSetting`,
  `TestBuildHostFW_AdmitsVRRPOnFHRPInterfaces`).
- user.md: the example enables `hostfw`; serving on a non-owner VIP needs
  `accept-mode: true`.

## Codex #1716 round 5

- Takeover neighbor advertisements, which gatewayd now sends through the
  default netlink programmer, set Router and Override (0xA0000000), so a
  client keeps the virtual gateway in its Default Router List (RFC 4861
  7.2.5) (`TestNeighborAdvertisementBody`,
  `TestNetlinkProgrammer_AnnounceSendsAnUnsolicitedNA`).

## Codex #1716 round 4

- A non-owner runner removes any VIP it finds before Startup, so a
  restarted backup under a live master never answers ARP/ND for it
  (`TestSpeaker_RestartedBackupRemovesAStaleVIP`).
- hostfw VIP denies match every ingress interface, are deduplicated by
  address, and sit before the established/related allowance
  (`TestRender_VIPDeny`, `TestRender_VIPDenyDeduplicatesAddresses`).

## Codex #1716 round 3

- A non-owner (priority < 255) runner adopts a VIP already on the
  interface (a crashed master's) and releases it on demotion and Stop;
  only a priority-255 owner keeps a preexisting address
  (`TestSpeaker_AdoptsAStaleVIPAfterRestart`).
- accept-mode false on a non-owner group: hostfw `VIPDeny` drop rules for
  the VIPs (IPv6 ND still answered), fed by `buildHostFW`; `Validate`
  refuses that config without hostfw (`TestRender_VIPDeny`,
  `TestBuildHostFW_DeniesVIPsWithoutAcceptMode`,
  `TestGatewayConfig_FHRPAcceptModeOffNeedsHostFW`).

## Slice 2: docs follow the wiring

- engineering.md lists `fhrp` (and `nat64`) among `serviceBuilders` and
  in the start order (tunnels, fhrp, transit); architecture.md's builder
  table gains `fhrp` and drops "not wired into gatewayd"; user.md drops
  the "not wired" and "hostfw does not admit VRRP" caveats. Docs only,
  so the slice 1 tests stand as the proof.

## Slice 3: VIP cleanup survives a failed rollback or stale removal

- A handler whose rollback Stop fails is recorded for Stop to retry
  (`TestGatewayStop_RetriesARollbackStopThatFailed`).
- A stale VIP the speaker cannot remove at Start stays pending (the
  group's releaseErr, plus older-length prefixes in `runner.stale`), and
  Stop or the next Start removes it
  (`TestSpeaker_StartFailsWhenTheStaleVIP*`,
  `TestSpeaker_NextStartRemovesAStaleVIPAnEarlierStartCouldNot`).
- A start rollback with cleanup pending (a failed handler kept its cleanup,
  or a rollback Stop failed) keeps the host firewall, the earlier services
  and the pipeline up until Stop finishes that cleanup (Codex P1, node.go;
  `TestGatewayStart_PendingCleanupKeepsEarlierServicesUp`).

## Slice 4: a part-way shutdown is retried; removed groups' VIPs swept

- Gateway.Stop drops each service from the active set as soon as its
  Stop succeeds, so a Stop that fails part-way is retried from the service
  that failed (an FHRP VIP still to release), not from overlay
  (`TestGatewayStopRetriesAfterAPartialFailure`).
- The speaker records every VIP it adds or adopts in `fhrp/vips.json`
  (the datapath row's new `fhrp` StateDir, written atomically); before
  any service starts, the gateway deletes the recorded VIPs of groups no
  longer configured, FHRP disabled included. An owner's own address is
  never recorded, so never swept (`TestFHRPSweepsVIPsOfRemovedGroups`).

## Slice 5: Codex #1716 round 3 on the VIP sweep

- Only the process that owns the datapath and FHRP sweeps at Start
  (`Gateway.ownsFHRPAddresses`); routing, proxy, VPN and parser children,
  and a supervisor whose FHRP runs in a child, never read the inventory
  (`TestGatewayStartSweepsOnlyInThePrivilegedProcess`).
- A recorded VIP stays only while its group still configures that address
  (`TestFHRPSweepsAddressRemovedFromARetainedGroup`).
- A runner restores ownership of inventory-recorded VIPs before Claim
  classifies a present address as a priority-255 owner's own
  (`TestSpeakerRestoresInventoryOwnedVIPAfterCrash`).
- A delete that fails on netlink's LinkNotFoundError forgets the entry;
  other failures keep it (`TestInventorySweepForgetsVIPOnMissingInterface`).
- Codex round 4 (#1716): a present, unrecorded stale VIP is owned before
  the fallible Inventory.Record, so a failed write keeps it pending for
  Stop (`TestSpeaker_StaleVIPCleanupSurvivesAnInventoryRecordFailure`);
  both Release loops treat LinkNotFoundError as a completed delete
  (`TestSpeaker_ReleaseTreatsAMissingInterfaceAsReleased`).
