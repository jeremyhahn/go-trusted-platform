# #1696: wire the FHRP speaker into gatewayd

## Objective

`pkg/sdn/fhrp` has a complete VRRPv3 speaker, but gatewayd never builds
it: `serviceBuilders` has no `fhrp` entry and `GatewayConfig` has no
`fhrp` section (docs/gateway/engineering.md, "not in gatewayd yet").
This row makes an enabled `fhrp:` section start the speaker as a gateway
service in the datapath process.

## Slice 1 (this lane)

Tests first (`test(gateway): ...`):

- `TestBuildFHRP_StartsSpeakerWithInjectedTransport`: an owner group
  (priority 255) over a fake Transport and Programmer; Start opens the
  group's socket on the configured interface and claims its address.
- `TestBuildFHRP_InvalidConfigRefused`: a group with VRID 0 is refused by
  `GatewayConfig.Validate` with `*ErrFHRPConfigInvalid` and by
  `buildFHRP` with `*ErrServiceStartFailed`.
- `TestEnabledServices_FHRP`: `fhrp` is enabled only when the section is.
- `TestClassTable_FHRPRunsInTheDatapath` (process): `fhrp` maps to the
  `datapath` process.

Change (`feat(gateway): ...`):

- `ServiceFHRP = "fhrp"` (node.go); `GatewayConfig.FHRP *fhrp.Config`
  (types.go), in `EnabledServices` when `Enabled`, validated in
  `GatewayConfig.Validate` (typed `ErrFHRPConfigInvalid`, errors.go).
- `HostRuntime.FHRPTransport` / `FHRPProgrammer` (runtime.go); nil falls
  back to `fhrp.NewRawTransport` / `fhrp.NewNetlinkProgrammer`.
- `buildFHRP` and the `fhrpBackend` adapter (handlers.go).
- `ServiceFHRP` among the `datapath` services (process/class.go).

Docs: docs/gateway/engineering.md drops the "not in gatewayd yet" line.

## Codex #1716 round 4

- A non-owner runner removes any VIP it finds before Startup, so a
  restarted backup under a live master never answers ARP/ND for it
  (`TestSpeaker_RestartedBackupRemovesAStaleVIP`).
- hostfw VIP denies match every ingress interface, are deduplicated by
  address, and sit before the established/related allowance
  (`TestRender_VIPDeny`, `TestRender_VIPDenyDeduplicatesAddresses`).

## Codex #1716 round 3

- A non-owner (priority < 255) runner adopts a VIP already on the
  interface (a crashed master's) and releases it on demotion and Stop;
  only a priority-255 owner keeps a preexisting address
  (`TestSpeaker_AdoptsAStaleVIPAfterRestart`).
- accept-mode false on a non-owner group: hostfw `VIPDeny` drop rules for
  the VIPs (IPv6 ND still answered), fed by `buildHostFW`; `Validate`
  refuses that config without hostfw (`TestRender_VIPDeny`,
  `TestBuildHostFW_DeniesVIPsWithoutAcceptMode`,
  `TestGatewayConfig_FHRPAcceptModeOffNeedsHostFW`).

## Slice 2: docs follow the wiring

- engineering.md lists `fhrp` (and `nat64`) among `serviceBuilders` and
  in the start order (tunnels, fhrp, transit); architecture.md's builder
  table gains `fhrp` and drops "not wired into gatewayd"; user.md drops
  the "not wired" and "hostfw does not admit VRRP" caveats. Docs only,
  so the slice 1 tests stand as the proof.

## Out of scope

- Snapshot/telemetry of the FHRP groups (an Observer feeding gwstate).
- A CLI or gateway-template `fhrp:` example; integration tests with real
  raw sockets (they need CAP_NET_RAW).
- Any lower-module bump: the pinned tags are enough.
