# #2016: mTLS callers are decided by the IAM PEP, not the wildcard scope

## Objective
A caller authenticated only by its mTLS client certificate today carries the
wildcard scope `*:*` (`mtlsOperatorScope`), so every scope check admits it.
Each transport must instead ask the IAM policy enforcement point (PEP) for
the certificate principal (subject, tenant), and deny on a missing checker,
an error or a refusal.

## Slices
1. QUIC (this slice).
   - `pkg/api/quic`: `PeerAuthorizationChecker` +
     `WithQUICPeerAuthorizationChecker`; `authenticatePeer` marks the context
     as a certificate principal and stores the checker; `AuthorizeRequest` and
     `AuthorizeSubOpcode` ask the checker before any scope check.
   - `pkg/api/daemon`: `iamTokenAuthorizer.CheckPeerPermission` asks the PEP
     for `authCtx.Subject` in `authCtx.TenantID`; `selectQUICAuth` wires it
     under mTLS.
   - Tests: `TestAuthorizeRequest_PeerPrincipalDecidedByPeerChecker` (no
     checker, deny, error, allow; also via `AuthorizeSubOpcode`).
2. REST: `route_scope.go`, daemon `rest_scope.go`, `iam_rest.go`,
   `device_rest.go` ask the PEP for a peer principal. Tests per route guard.
3. MCP: `authz.go` asks the PEP for a peer principal; then delete
   `mtlsOperatorScope` once no transport uses it.

## Status (slice 1)
Done: `pkg/api/quic` peer checker + tests. Remaining: daemon wiring, i.e.
`iamTokenAuthorizer.CheckPeerPermission`, which calls `checkPrincipalPermission`
with `{Subject, TenantID}` from authCtx, and appending
`quic.WithQUICPeerAuthorizationChecker(&iamTokenAuthorizer{pep: pep})` in
the `selectQUICAuth` mTLS branch when pep != nil. Until then daemon QUIC
mTLS callers are denied (fail closed). `mtlsOperatorScope` stays: MCP and
REST still use it.

## Out of scope
gRPC mTLS interceptor (separate row), PEP policy content, go.mod changes.
