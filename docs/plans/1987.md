# Plan #1987: auth-factor administration decided by IAMPEPClient.Check

## Objective

`callerAuthorized` in `pkg/api/rest/auth_factor_handlers.go` admits a caller
with no TLS peer, a certificate CN starting with `admin`, or an OU `admin`
(the OU names the tenant, so that check reads a tenant name as a role).
Replace it with a PEP decision on go-qrdb's auth-factor permission for the
session principal; a request with no authenticated principal is refused.

## Design

- `pkg/api/rest` cannot import `pkg/api/daemon` (daemon imports rest), so the
  handlers take two injected seams:
  - `AuthFactorPEP` interface: `Check(ctx, *sdkiam.CheckRequest)
    (*sdkiam.CheckResponse, error)` (satisfied by `quicbaassdk.IAMPEPClient`,
    sdkiam = `go-quicbaas/sdk/go/client/iam`);
  - a principal resolver `func(*http.Request) (AuthFactorPrincipal, bool)`
    returning Subject, TenantID, Roles.
- `AuthFactorHandlers` gains `pep` and `principal` fields, set by a
  `WithAuthorization(pep, principal)` method so the existing
  `NewAuthFactorHandlers(ca, logger)` callers (tests) keep compiling.
- `callerAuthorized`: no resolver / no principal / empty Subject or TenantID
  -> false; nil PEP -> false; else `pep.Check` with the principal and the
  auth-factor resource/action; error -> false; `resp.Allowed`.
- Production wiring: `pkg/api/daemon/rest_service.go` (line ~550) passes the
  daemon's `iamService.PEP()` and a resolver over `restCaller(r)`
  (`platformtoken.AuthorizedContext`: Subject, TenantID, Roles).

## Findings (slice b)

- `callerAuthorized` has one caller: `handleIssueCert` (403 on false).
- SDK types: `sdkiam.CheckRequest{Subject: sdkiam.CheckSubject{ID, TenantID,
  Roles}, Action, Resource, TenantID}`; `CheckResponse.Allowed`. Pattern to
  copy: `checkPrincipalPermission` in `pkg/api/daemon/quic_iam_authorizer.go`.
- Permission (Codex round 1, #2079): go-quicbaas forwards Resource/Action to
  go-qrdb RBAC (`resource:action`); its vocabulary has `authfactor:enroll`, so
  the check sends Resource `authfactor`, Action `enroll` (target user from
  the route). The earlier `auth_factors:issue-cert` matched nothing.
- The daemon wires CA handlers (`SetCAHandlers`, daemon.go ~1567) BEFORE the
  IAM PEP exists (daemon.go ~1600, `iamService.PEP()`). Plan: keep the
  handlers in a new `RESTServer.authFactorHandlers` field; add
  `RESTServer.SetAuthFactorPEP(pep)` called in the `sdkPEP != nil` branch at
  daemon.go ~1601. PEP nil until then -> deny (fail closed).
- `restCaller(r)` is only set by the `catalogAuthorization(guard).authorize`
  middleware (`catalogGuardedAPI`/`catalogGuardedRoot`, rest_scope.go ~218);
  `SetCAHandlers` registers auth-factor routes on the bare `s.router`, so the
  resolver over `restCaller` sees no principal. Done (Codex round 1): the
  catalog has no auth-factor routes, so issue-cert mounts on a subrouter with
  `authFactorAuthorization(guard).authorize` (iam scope by method), via
  `RegisterRoutesWithIssuer`; test `rest_auth_factor_route_test.go`. AAGUID,
  probe and MFA policy stay unguarded (route-guard test exception list).
- Existing tests to update (they pass with no TLS / CN match today):
  handlers_test `TestIssueCert_ValidCSR_ReturnsCert`, `_InvalidCSR_`,
  `_MissingCSRPEM_`, `_SameUserAsCaller_Succeeds`; apirest_test
  `TestAuthFactorAPIRest_IssueCertErrors`, `_CallerAuthorized` table. Give
  `newHandlerWithCA` an allowing fake PEP + principal.
