# Plan: #178 — bootstrap seeder authenticates over mTLS

## Objective

The device template and profile routes the bootstrap seeder calls
(`/api/v1/devices/...`) are gated by the control plane's mTLS middleware,
and the seeder authenticates as `admin@system` with the firstboot admin
bundle. No new credential machinery: it uses what the stack already
produces.

## Slices, in order

1. **Seeder presents a client certificate** (this slice).
   - `SeederParams.ClientCertificate *tls.Certificate`: the firstboot admin
     bundle (`admin@system`). `NewSeeder` puts it in the HTTP client's
     `TLSClientConfig.Certificates`; nil keeps today's behaviour.
   - Test: `TestSeederContract_PresentsClientCertificate` runs the contract
     router behind a TLS server that requires and verifies a client
     certificate (in-test ECDSA P-256 CA, client cert CN `admin@system`,
     ExtKeyUsageClientAuth). Seed with the certificate uploads the template;
     Seed without it returns an error and stores nothing.
2. **Gate the device routes and wire the bundle** (later lane).
   - `restdevice.NewDeviceRouter` takes a middleware parameter and is given
     `MTLSMiddleware()`, matching its sibling routers.
   - The orchestrator loads the firstboot admin bundle and passes it as
     `SeederParams.ClientCertificate`.
   - Tests: an unauthenticated `POST /api/v1/devices/templates` is refused;
     the same call with the firstboot admin client certificate succeeds.

Slice 2 cannot land first: without slice 1 the seeder has no client
certificate and seeding would fail closed.

## Out of scope

- New credential issuance or rotation for the seeder.
- Changes to the mTLS middleware's verification rules.
