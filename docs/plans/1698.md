# Plan: #1698 gatewayd hosts the WireGuard VPN plane in the datapath child

SPEC row: `vpn` (docs/SPEC.md Features).

## Objective

`vpn.NewPlaneHost` (`pkg/sdn/gateway/services/vpn/datapath_host.go`) and
`ipc.Server.SetVPNPlanes` (`pkg/sdn/gateway/ipc/server.go`) have no
production caller: the datapath child served by
`pkg/sdn/gateway/commands/service.go` answers every `InstallVPNPeer` with the
`noVPNPlanes` refusal. This row wires the VPN planes into the datapath child
of gatewayd so the peer RPCs reach a real plane.

## Slices

1. WireGuard plane in the datapath child (this slice).
   - `datapathVPNPlanes(def, cfg, gw, logger)` in `commands/service.go`:
     only for the kernel datapath class and only when `management_vpn` is
     enabled; builds a WireGuard plane (`!fips` builds) from
     `tunnel.NewWireGuardHub` with `management_vpn.wireguard.listen-port` and a
     key from `HostRuntime.SecretResolver` (through `resolverKeyProvider`),
     wraps it in `vpn.NewPlaneHost`, and hands it to `server.SetVPNPlanes`
     before `Listen`; the plane is started and stopped with the child.
   - The plane factory sits on the existing `deps` seam so tests inject a
     fake plane.
   - Tests (package `commands`):
     - `TestServeProcess_DatapathHostsVPNPlanes`: an injected fake plane
       answers `InstallVPNPeer` through `ipc.Client`.
     - `TestDatapathVPNPlanes_DisabledLeavesRefusal`: `management_vpn`
       disabled leaves the `noVPNPlanes` refusal in place.
     - `TestDatapathVPNPlanes_NonKernelClassNone`: a non-kernel class gets
       no planes.
   - Docs: `docs/vpn/engineering.md` lines 5 and 89 say the assembly exists.
1b. The production plane factory (finishes slice 1, draft PR #1717).
   - New keys `management_vpn.wireguard.key-ref` and
     `management_vpn.wireguard.address` (`vpn.WireGuardSettings`), refused
     only while wireguard is not offered (1d).
   - `vpnDataPlanes` moves to `service_vpn_planes.go` (`!fips`): it builds
     `tunnel.NewWireGuardHub` ("vpn-hub0", key-ref, listen-port, address)
     over the host's `SecretResolver` and wraps it in `vpn.NewWireGuardPlane`;
     no plane (a Warn) while wireguard is not offered, either key is unset or
     there is no resolver. `service_vpn_planes_fips.go` builds none.
   - Tests (`service_vpn_planes_test.go`): `TestVPNDataPlanes_*` (builds the
     plane; missing key-ref, invalid address, no resolver, not offered).
   - Docs: line 5 and the §5 key table name the two keys.
1c. Codex round-1 P1s on #1717 (a test commit, then a fix commit, each).
   - Restart: `WireGuardHub.Up` replaces a stale WireGuard device of its
     name (EEXIST after a SIGKILL'd predecessor), refuses a foreign one
     (`TestWireGuardHub_UpReplacesAStaleHubDevice`, `..._UpRefusesAForeign...`).
   - Readiness: a plane that fails to start keeps `gw.Start` from running,
     so no hosted service reports active (`TestServeProcess_PlaneFailure...`).
   - Host firewall: `buildHostRuntime` lists the hub's UDP listen port in
     `HostRuntime.Listeners` (`!fips`), so hostfw admits handshakes.
1d. Codex round-2 P1s on #1717 (a test commit, then a fix commit, each).
   - Validation: `wireguard.key-ref` and `wireguard.address` are refused
     while wireguard is not offered (MASQUE-only and every `fips` build).
   - Stale peers: `WireGuardHub.Up` removes its own stale device before it
     resolves the key, so a key-store failure leaves no predecessor peers.
   - Peer replay: after a datapath restart the surviving VPN leases are
     installed into the new plane before readiness is reported. No new IPC
     verb: `process.Definition.FollowsDatapath` (set on `vpn`) makes the
     supervisor relaunch the vpn child once the relaunched datapath child
     answers; the vpn start's `Restore` reinstalls every stored lease, and
     the vpn service stays down (restoring) until that start is done
     (`TestRelaunch_ADatapathRestartRelaunchesTheVPN...`).
1e. Codex round-3 P1s on #1717 (a test commit, then a fix commit, each).
   - Stale hub: a kernel-class child that hosts no plane (VPN disabled, no
     key-ref/address/resolver) removes `vpn-hub0` itself
     (`tunnel.RemoveStaleWireGuardHub`); a removal failure stops the child.
   - Overlapping relaunch: a datapath restart while the vpn child is still
     launching queues a second vpn relaunch for when that launch completes.
1f. Codex round-4 P1s on #1717 (a test commit, then a fix commit, each).
   - Stale lookup: only a typed link-not-found counts as no stale hub;
     any other `LinkByName` error stops the child.
   - FIPS: deletion-only `tunnel.RemoveStaleWireGuardHub` is untagged, so a
     FIPS datapath removes a non-FIPS predecessor's `vpn-hub0` too.
   - VPN restart: `Restore` reconciles the hosted planes' peers against the
     stored leases over a new `DatapathService.ReconcileVPNPeers` verb, so a
     peer whose record a revoke deleted before the child died is removed.
   - Follower retry: a relaunched vpn whose service reports inactive or a
     StartError is relaunched again, not taken as recovered.
1g. Codex round-5 P1s on #1717 (a test commit, then a fix commit, each),
   plus the staticcheck embedded-field selector in `service_vpn_planes.go`.
   - Rejected lease: `restore` removes a hosted plane's peer before it drops
     a lease it rejects, and keeps the address if removal fails.
   - Reconcile retry: a failed peer reconciliation (or rejected-peer
     removal) leaves a per-plane obligation that `Sweep` retries, under the
     enrolment gate, until it succeeds; then held addresses are released.
2. MASQUE plane in the datapath child (later slice).
3. `FactorVerifier` wiring (later slice; needs a go-quicbaas verb not in
   v0.12.0-alpha).
