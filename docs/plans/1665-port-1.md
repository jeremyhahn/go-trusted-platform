## Gaps for the route audit

A mocked case with no server state the SDK can seed (no BMC, no TPM
device, no collector report) is ported to assert whatever the server
really answers (success or its refusal shown verbatim); a case with no
server behaviour behind it is listed here.

- Specs 1-9: the slice that ported them recorded no gap list (its
  commits say every case reads the server's answer); a gap found when CI
  runs them is added here.
- compute-vms: the harness daemon has no hypervisor seeded, so it may
  list no VM; then each VM-detail case asserts only that the server
  refuses an unknown VM id. The mocked fixed answers (running/paused
  state toggle, CPU 42%, 2 PCR values, snapshot of 4096 bytes, receiver
  rx-42 on port 49152, committed receiver) have no seeded server state:
  the port asserts the request body and the page's handling of whatever
  the server answers. The harness needs a seeded VM (route audit).
- compute: the VM, container and snapshot cases seed through the SDK
  (createVM, createContainer, createSnapshot); with no compute backend the
  seed is refused and each case asserts the list state the server answers
  (503 SERVICE_NOT_CONFIGURED shows "not available", any other refusal an
  error). Not portable without a server that can be made to answer them:
  the three 503 classification cases (transient 503, registry prose under
  a non-503, 503 without the discriminator) and the delayed-answer loading
  spinner; the page's classification needs a unit test (route audit). The
  three error-state cases merge into the operation cases' refusal branch.
  The tenant-member view needs a second, member account in the harness
  (route audit); the admin view is ported.
- dashboard: the harness's real-server/dashboard.spec.ts ports the rest
  and lists its own gaps (degraded health, network/loading/API-error
  fulfilments, member access, fixed counts). dashboard-port adds the two
  cases it neither ports nor lists: the sections shown once the server has
  answered, and the Certificates stats card link. Member Access "display
  navigation for members" falls under the harness's member-access gap.
- device-lookup: devices and profiles seed through the SDK (createDevice,
  createProfile). The fixed counts (42 devices, 7 profiles) become "at least
  the seeded one". No server state the SDK can seed: an enrolled device the
  server admits on activate-json (VLAN 20), the calling device's own profile
  (GET /device/profile answers a device session, not the admin), and a
  profile linked to a device serial (profiles/serial/<serial>); each asserts
  the request and the page's handling of the server's real answer.
  UpdateProfile finds the profile by MAC instead of by serial for that
  reason. The harness needs an enrolled device (route audit).
- device-templates: templates and profiles seed through the SDK
  (createTemplate, createProfile with an EK serial). The mocked base64
  config round trip is not ported: the SDK types config as JSON while the
  server stores bytes (route audit). No seedable server state: an enrolled
  device to assign a profile to or unassign it from, so Assign and Unassign
  assert the request and the page's handling of the server's answer;
  FindConfig asserts the match when the server matches the seeded EK serial
  and its 404 answer otherwise.
- eab: credentials seed through the SDK (eab.create, profile id 7 or one
  above 2^53) in the harness admin's tenant; the server's ids replace the
  fixed ids 1, 2 and 99 (an unknown id is a seeded and deleted one). The
  mocked expired credential has no seedable server state (the SDK sets no
  past expiry): the list case shows a revoked one instead, and the cleanup
  case asserts the server's count and that an active credential survives.
  The harness needs a way to expire a credential (route audit).
